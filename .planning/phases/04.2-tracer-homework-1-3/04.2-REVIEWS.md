## Codex Review (codex-glm)

I’ve read the repo enough to ground the review in actual files and line numbers. Overall, the phase design is coherent, but two plan-level issues are likely to cause real execution failures: the scaffold verification in `04.2-01` and the Wokwi timing in `04.2-03`.

## 04.2-01

### Summary

Strong plan for the correct homework ID, real provenance, and the only supported scaffold path. It maps well to `AGENTS.md` and `scripts/new_homework`, but the task-level verify has an idempotence bug: after the real scaffold already exists, a second `--dry-run` will report `UNCHANGED`, not the `CREATE` values the verifier demands.

### Strengths

- Correctly uses `scripts/new_homework` as the only supported creation path (`AGENTS.md:106-107`), and the scaffold is genuinely atomic/idempotent because `scripts/new_homework:298-321` classifies identical bytes as `UNCHANGED`, never overwrites them.
- Metadata/provenance handling is grounded in the actual checker:
  - `retrieved` must be ISO 8601 with a timezone (`scripts/metadata/contract.py:138-144`).
  - `TODO` sentinels are accepted only while status is `planned` (`scripts/metadata/contract.py:240-246`).
  - The source URL cross-check is an error, not a warning (`scripts/metadata/contract.py:284-301`).
- The friction log is started at the right point, matching D-20.

### Concerns

- **HIGH — verify is self-contradictory after successful scaffold.** Plan `04.2-01:156` starts verification by running `new_homework --dry-run --json` and asserts `all(x["status"]=="CREATE" for x in r)`. But once the scaffold exists and the content is unchanged, `scripts/new_homework:318-321` returns `UNCHANGED`, not `CREATE`. Unless the executor deliberately runs verify before the action, this fail-safe will make task 1 fail on success.
- **MEDIUM — generated path guard is indirect.** The acceptance criteria mention no `.pio/`, `compile_commands.json`, or `firmware*.bin` (`04.2-01:160-164`), but the automated verify does not itself assert the staging state. It relies on later pre-commit behavior.
- **LOW — report is intentionally absent in this wave.** Plan 01 sets up the project but not `report.md`; this is acceptable only because plan 04 explicitly creates it.

### Suggestions

- Change the verify to accept either `CREATE` on the first run or `UNCHANGED` on re-run, and remove the duplicate real scaffold invocation after the action.
- Add an explicit `git diff --cached --name-only` / `git ls-files` check at the end of plan 01 to prove no generated artifact is staged.
- Keep the provenance timestamp correction, but record it in the friction log exactly as done.

### Risk assessment

**MEDIUM-HIGH** — the architecture and provenance work is strong, but the current verify will likely reject a correctly completed scaffold.

## 04.2-02

### Summary

The code plan is architecturally sound: it keeps domain logic in the homework-local private library, uses the existing port contracts and host fakes, and defines the controller seam every later homework will copy. The main weakness is incomplete automated coverage of a promised architectural invariant.

### Strengths

- Correctly builds on the validated private-library mechanism. `lib/pattern` will be auto-discovered by both target and native environments, and the research note about omitting `frameworks`/`platforms` matches the shared-library behavior (`templates/homework-arduino/platformio.ini:12-31`, `lib/common/library.json:1-7`).
- Controller design is testable through real repository contracts (`lib/port/include/port/gpio.h`, `lib/port/include/port/time.h`), and the fake clock/GPIO behavior is accurately understood (`lib/host/src/fake_gpio.c:63-77`, `lib/host/src/fake_time.c:18-28`).
- Use of `common_elapsed_ms` and `common_debounce_update` is grounded in current code (`lib/common/include/common/timing.h:29-45`).
- The task 3 verify is the strongest one in the plan set: it runs build, metadata, architecture, and native tests together (`04.2-02:303-306`).

### Concerns

- **MEDIUM — framework-header exclusion is not mechanically enforced for `homeworks/**`.** `scripts/check_architecture.py:223-240` classifies files under `homeworks` as owner `homeworks`; external-header allowlists only apply to shared-library owners (`scripts/check_architecture.py:350-383`). So the architecture checker alone cannot prove `lib/pattern` has no framework headers. The target build will catch obvious `Arduino.h` inclusion, but the plan’s statement is stronger than the check.
- **MEDIUM — task 1 does not verify the target build.** Task 1 builds logic and `main.cpp` but verifies only native tests and the architecture checker (`04.2-02:180-183`). Target build is not verified until task 3. This means a target-only compile issue can surface late.
- **LOW — controller boundary is slightly under-specified.** The plan describes debounce, long press, mode changes, and timing, but not the exact behavior of a failed `read` during tick or whether failed writes should leave the controller unusable until re-init.

### Suggestions

- Add a small task 1 target-build check, even if it can be a temporary build without the controller.
- Add a lightweight grep/AST check for `Arduino.h` and framework headers in `lib/pattern/**` until the architecture checker itself is strengthened.
- Specify controller behavior on failed read/write and whether ticking stops, retries, or remains ready.

### Risk assessment

**LOW-MEDIUM** — architecture is sound; the main concern is that some stated invariants are not yet mechanically checked.

## 04.2-03

### Summary

This plan correctly captures the Wokwi and firmware-image friction, and the wiring is the right half-bridge interpretation. However, the generated scenario appears to be timing-inconsistent with the pattern from plan 02. This is the most likely future execution failure in the phase.

### Strengths

- The diagram uses verified Wokwi pin forms and board attributes; the plan explicitly avoids the `3V3` and `43/44` pitfalls (`04.2-03:128-160`).
- The merge script is well-scoped: it imports only `os`, writes only `$BUILD_DIR`, and uses the corrected `tool-esptool` / `merge-bin` path (`04.2-03:187-215`).
- Offline lint is the correct evidence level without a token; plan 03 does not falsely claim simulation success (`04.2-03:156-160`, `214-226`).
- The `extra_scripts` inheritance trap is handled correctly because the child environment repeats the inherited `pre:../../scripts/pio/compiledb.py` entry (`04.2-03:197-215`, `platformio.shared.ini:16`).

### Concerns

- **HIGH — scenario timing contradicts the alternating pattern.** Plan 02 defines alternating mode with four frames of one base each, and speed index 0 is 400 ms (`04.2-02:157-162`). Plan 03 then creates a scenario that waits for `pattern ready` and delays 500 ms before expecting GPIO4 high (`04.2-03:202-205`). If `pattern ready` is logged immediately after applying frame 0, a 500 ms delay crosses frame 1, when GPIO4 should be LOW. Unless the scenario intentionally selects a different timing mode, this check will fail during actual execution.
- **MEDIUM — `--diagram-file` is mentioned in context but not repeated in the scenario execution path.** The action names it, but `scenario.yaml` and `wokwi.toml` should make this less fragile.
- **MEDIUM — the `ast.Import` allowlist is too narrow.** The verify only checks `ast.Import` nodes, not `ast.ImportFrom` nodes (`04.2-03:215-216`). If the executor writes `from os.path import join`, the check would pass vacuously; a stronger check should inspect both node types plus calls to prohibited host facilities.
- **LOW — merge script is project-local, which is deliberate but still duplication risk.** This is already flagged for Phase 7; it should remain project-local for the tracer.

### Suggestions

- Change the scenario to `delay: 100ms` or otherwise assert within the current alternating frame, or choose an explicit frame where GPIO4 is known HIGH.
- Strengthen the Python AST check to inspect `ast.Import` and `ast.ImportFrom`, and reject network/subprocess modules.
- Add a small assertion that `scenario.yaml` can be parsed and that the first few steps are coherent with the firmware’s initial frame timing.
- Record the corrected scenario timing as its own friction entry; it is exactly the kind of integration pain this phase should log.

### Risk assessment

**MEDIUM-HIGH** — the wiring and merge work are solid, but the current scenario is likely to fail when it is eventually run in Phase 7.

## 04.2-02

**Summary.** Implements the core deliverable's risky, irreversible decisions: a homework-local private `lib/pattern` library with `library.json` omitting `frameworks`/`platforms`, a C controller behind `port_gpio_t`/`port_time_t` with host-fake tests, and the Arduino composition root. The `extra_scripts`-style mechanism and the contract types were actually verified against the repository's port and fake headers.

**Strengths.**
- The private-library mechanism is correctly scoped: omitting `frameworks` is required because the `[env:native]` environment has no `arduino` framework and `lib_compat_mode = soft` would silently drop the library (research Pitfall 2). Verified as the five shared manifests do exactly this (`lib/port/library.json`, `lib/common/library.json`).
- Contract injection is real: `port_gpio_t`/`port_time_t` are defined in `lib/port/include/port/gpio.h` and `time.h` with `void *ctx`, and the fakes in `lib/host/include/host/fake_gpio.h`/`fake_time.h` return identical struct types — signature drift becomes a compile error.
- `common_debounce_update` (`lib/common/include/common/timing.h`) is reused rather than re-implemented, satisfying ARCH-04 and the "don't hand-roll" list.
- The boundary test (399 ms must not advance, 400 ms must) is a genuinely sharp edge case, not a nominal case dressed up.

**Concerns.**
- **HIGH** — The controller contract in `must_haves.truths` says "one frame per tick" but also "Mode and speed changes reset the step index and step start", and `pattern_speed_base_ms` for `index 0..2` returns 400/200/100. There is no spec for what happens if `host_fake_time_advance` goes backwards or wraps; `common_elapsed_ms` uses unsigned subtraction so a large delta reads as huge. The tests should bound this. Without such a test, a hidden regression in frame scheduling could ship. Recommend adding a wrap-around case.
- **MEDIUM** — `lib/pattern` includes `common/timing.h` and `port/*.h`, but the private library's `library.json` declares no dependencies. On PlatformIO, includes of symlinked libraries resolve because the project's `lib_deps` lists them, and project-local `lib/` is discovered first. This works empirically (research verified it), but it is implicit ordering; if a later review "cleans up" `lib_deps`, pattern breaks silently. Worthy of a friction-log entry (plan 07 mentions it).
- **MEDIUM** — `PATTERN_CONTROLLER_LONG_PRESS_MS 600u` with a 30 ms debounce: the door is open for a button pressed for ~620 ms to be classified as a "long press" without a stable-push confirmation window. The debounce only stabilises the *level*, not the duration intent. Recommend documenting acceptable release-on-a-mid-press behaviour as a known limitation.
- **LOW** — The "all-off frame drives pin A to `PORT_GPIO_INPUT`" single-GPIO claim only works if the half-bridge node actually goes high-impedance; on a real GPIO outputs LOW keeps current flowing through one LED. The plan states "all-off frame sets the pin to INPUT so both LEDs are dark" — on hardware an INPUT pin with no pull-up floats at the LED clamp voltage, not truly dark. This is a subtle real-hardware deviation and the report (plan 04) must not over-claim. Flag as a TRACE entry.
- **LOW** — Using `host_fake_gpio_fail_next` injection is good; failure path `status` bookkeeping should be cleared between cases. The plan's tests should call `host_fake_gpio_reset` in `setUp`; it's stated but worth enforcing.

**Suggestions.**
- Add a wrap-around elapsed-time test to `test_pattern`, mirroring `tests/test/test_common_timing/test_timing.c`.
- Record the half-bridge "dark frame" fidelity caveat in the decision appendix (plan 05).

**Risk level:** MEDIUM. Irreversible shape decisions (D-06, D-07) cannot be cheaply reworked, and the plan is honest about that, but the timing contract is incompletely bounded.
