## Accomplishments

- Added `homeworks/1_3-police-flasher/lib/pattern/` with a manifest that deliberately omits
  `frameworks` and `platforms`, so the same pure C sources compile into both
  `[env:esp32s3_arduino]` and `[env:native]` with no `lib_deps` entry and
  `test_build_src = false`.
- Modelled every mode as data: alternating (4 frames), double flash (8), chase (4), and solid
  (1), each row carrying three LED flags and a rational hold `base * num / den`. The mode
  cycle wraps ALTERNATING → DOUBLE_FLASH → CHASE → SOLID, the speed cycle is 400/200/100 ms,
  and an invalid mode or step is one all-off frame with the caller's base hold.
- Built the controller seam: a debounced button with short-press mode cycling and long-press
  speed cycling, exactly one frame per tick, `step_started_ms += hold_ms` for no drift, a
  one-hold-behind resync for no burst, a signed view of the elapsed difference so a backwards
  clock jump changes nothing, and read/write failure records with a same-value retry.
- Rewired `src/main.cpp` to `pattern_controller_init` and `pattern_controller_tick` only, at
  GPIO 4/5/6/7 with `PATTERN_GPIO_SINGLE`, writing `pattern ready` on success and
  `pattern init failed` otherwise.
- Proved the whole plan natively: 38 Unity cases in three suites, zero failures; the target
  build reports `SUCCESS`; `check_metadata.py`, `check_architecture.py`, and the explicit
  framework-include scan under `lib/pattern/` all exit 0.
- Recorded F-04..F-07 in the friction log, including the implicit `lib_deps` coupling and the
  two half-bridge limits that plan 04's report and plan 05's decision appendix must state.

## Decisions Made

- The pattern library is homework-local at `lib/pattern` with a manifest that omits
  `frameworks` and `platforms`; both environments discover it and no `lib_deps` entry is
  needed.
- `PORT_GPIO_INPUT` is a pin mode, not a write level. An all-off frame calls `set_mode(INPUT)`
  and leaving that state calls `set_mode(OUTPUT)` before the next write; each pin therefore
  tracks `applied`, `as_input`, and `level`.
- The controller applies the current frame before reading the button. This makes the
  plan-mandated one-shot `host_fake_gpio_fail_next` write test deterministic, and a mode or
  speed change re-applies the new frame in the same tick.
- The schedule advances at most one frame per tick and resyncs `step_started_ms` to `now`
  only when a stall leaves it more than one hold behind. The signed view of the unsigned
  elapsed difference treats a backwards clock jump as "not yet".

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] The all-off frame is a mode change, not a write**
- **Found during:** Task 2 (controller seam)
- **Issue:** The plan says an all-off frame "drives pin A to `PORT_GPIO_INPUT`", but
  `PORT_GPIO_INPUT` belongs to `port_gpio_mode_t`, not `port_gpio_level_t`, and the Arduino
  adapter returns `PORT_ERR_INVALID_ARG` for any write level other than LOW or HIGH. A
  literal write would fail on hardware and in the fake.
- **Fix:** The controller calls `set_mode(pin, PORT_GPIO_INPUT)` for the all-off state and
  `set_mode(pin, PORT_GPIO_OUTPUT)` before the next write, tracking the applied mode per
  pin.
- **Files modified:** `lib/pattern/include/pattern/controller.h`,
  `lib/pattern/src/controller.c`
- **Verification:** The native suite pins `fake.mode[4] == PORT_GPIO_INPUT` on the all-off
  frame and `OUTPUT` again on the next lit frame; the target build compiles the same code.
- **Committed in:** `390be45` (Task 2 commit), recorded as F-06.

**2. [Rule 3 - Blocking] Output application precedes the button read**
- **Found during:** Task 2 (controller seam)
- **Issue:** The plan requires a write-failure test injected with
  `host_fake_gpio_fail_next`, whose forced status is consumed by the next GPIO operation of
  any kind. With a read-first tick, the injected failure always hit the button read and the
  write path could not be exercised without a bespoke double.
- **Fix:** The tick advances the schedule and applies the current frame first, then reads and
  debounces the button; a mode or speed change re-applies the new frame at the end of the
  same tick.
- **Files modified:** `lib/pattern/src/controller.c`
- **Verification:** `test_a_failed_read_keeps_the_stable_level` and
  `test_a_failed_write_is_retried_on_the_next_tick` both pass; the latter asserts the old
  level survives the failed write and that the next tick retries it successfully.
- **Committed in:** `390be45` (Task 2 commit), recorded as part of F-05/F-06.
