# Phase 4.2 Friction Log — Tracer Homework 1.3

This log records where delivering the real homework `1_3-police-flasher` hurt, while the
work was fresh. It is the primary output of Phase 4.2: Phases 5 through 10 automate only
what this log proves painful (D-20). Each entry is a step of the delivery cycle, not a
bug report; the homework itself is the instrument that produced the evidence.

## How to read this log

Every entry carries the same seven fields:

- **step** — the delivery step in which the friction appeared;
- **what hurt** — the concrete obstacle, in the words of the person who hit it;
- **frequency** — how often a homework is expected to meet it;
- **cheap fix** — the smallest change that removes the hurt today;
- **automation candidate** — the script, hook, or generator that would pay off later;
- **what worked** — the existing repository mechanism that made the step possible;
- **minutes spent** — measured or estimated time lost to the friction.

`## Top automation candidates` stays empty until plan 07 synthesizes this log. The
`## Edge-probe dispositions` table is the no-silent-drop record for the fourteen
deterministic probe rows; its wording is fixed.

### F-04 — Private library discovery and the implicit `lib_deps` coupling

| Field | Value |
|-------|-------|
| Step | Add the homework-local `lib/pattern` library |
| What hurt | Two invisible coupling points decide whether the library builds at all. First, `library.json` must omit `frameworks` and `platforms`: declaring the Arduino framework makes the library disappear from `[env:native]` with `'pattern/pattern.h' file not found`, because the default `lib_compat_mode = soft` filters on an environment that has no framework. Second, the manifest declares no dependencies, so `pattern` compiles against `common` and `port` only because the homework's `lib_deps` lists both and PlatformIO resolves the project-local `lib/` first. A later "cleanup" of `lib_deps` would break the library silently, and no checker would report it. |
| Frequency | Every homework with pure logic — the shape every later homework is meant to copy. |
| Cheap fix | Keep the manifest to `name`, `version`, `build.srcDir`, and `build.includeDir`; never add `pattern` to `lib_deps`; keep the two shared entries in the homework's list. |
| Automation candidate | Phase 5's homework generator emits the manifest and the `lib_deps` block together, so neither can drift from the other (Phase 5, reused by the `new-homework` skill in Phase 9). |
| What worked | The same `lib/pattern/src/*.c` files compiled into the target build and the native test binary with `test_build_src = false` and no extra configuration. |
| Minutes spent | ~3 min, mostly spent confirming the `frameworks` failure mode and then removing the key. |

### F-05 — Native `-Werror` and the fake's default button level

| Field | Value |
|-------|-------|
| Step | Write the controller suite against `host/fake_gpio` and `host/fake_time` |
| What hurt | The native environment repeats `-Wall -Wextra -Werror`, so a signed/unsigned comparison or an unused local fails the test binary while the target build stays green — the opposite of the usual failure direction. Separately, `host_fake_gpio_reset` sets every pin to `PORT_GPIO_LOW`, which the controller reads as "button pressed"; an idle `INPUT_PULLUP` button must be seeded to `PORT_GPIO_HIGH` in `setUp`, and both fakes must be reset there so a forced status or a write counter cannot leak between cases. |
| Frequency | Every controller test that reads the button. |
| Cheap fix | Reset both fakes in `setUp`, seed the button level, and cast sizes explicitly when comparing with Unity's `unsigned` assertions. |
| Automation candidate | A test-scaffold block in the homework template that already resets both fakes and seeds the idle button (Phase 5/9). |
| What worked | `host_fake_gpio_fail_next` injects exactly one failure, which made both the failed-read and failed-write paths scriptable without a bespoke double. |
| Minutes spent | ~4 min, including one wrong ordering of the failure injection that init consumed. |

### F-06 — What the controller seam actually cost

| Field | Value |
|-------|-------|
| Step | Move the frame schedule and button handling behind `port_gpio_t` / `port_time_t` |
| What hurt | The seam is small, but one hardware fact is not expressible in the existing contracts: `PORT_GPIO_INPUT` is a pin mode, not a level, and the Arduino adapter rejects it as a `write` level with `PORT_ERR_INVALID_ARG`. An all-off frame therefore has to call `set_mode(INPUT)`, and leaving that high-impedance state has to call `set_mode(OUTPUT)` before the next write — a per-pin `(applied, as_input, level)` record, not the single "last applied levels" the plan sketched. The plan's phrase "drives pin A to `PORT_GPIO_INPUT`" is correct as an intent and wrong as a `write` call. |
| Frequency | Every homework whose output can be high-impedance; every future controller copied from this one. |
| Cheap fix | Track the applied mode alongside the level in the controller and treat the all-off state as a mode change. |
| Automation candidate | A shared output-state helper beside `port/gpio.h`, but only after a second homework needs it (D-05 keeps it homework-local for now). |
| What worked | Applying the frame before reading the button made a single-shot injected failure land on the pending write rather than on the button read, and a mode or speed change re-applies the new frame in the same tick. |
| Minutes spent | ~10 min, the largest single block in this plan. |

### F-07 — Two half-bridge limits that the report must state

| Field | Value |
|-------|-------|
| Step | Map the single-GPIO profile onto the half-bridge pair |
| What hurt | Two behaviours cannot be reproduced faithfully on one pin. An all-off frame leaves the shared node high-impedance (`PORT_GPIO_INPUT`), which is dark only in simulation; on hardware the floating node sits near the LED clamp voltage and may leave a faint glow. And `PATTERN_MODE_SOLID` drives the pin HIGH because `led_a` wins, so only the HIGH-lit LED of the anti-parallel pair lights while the LOW-lit one stays dark. Neither is a bug in the pattern logic, but a report that calls the off state "both LEDs dark" would claim a behaviour the circuit does not have. |
| Frequency | Every homework that uses one pin for an anti-parallel pair. |
| Cheap fix | State both limits in the report's decision appendix and label the simulated darkness as simulated. |
| Automation candidate | A report-contract checklist item for high-impedance and precedence limitations (Phase 10). |
| What worked | Keeping `led_a` and `led_b` explicit in the frame table makes the precedence rule testable in data and in the controller instead of hiding inside the adapter. |
| Minutes spent | ~2 min. |
