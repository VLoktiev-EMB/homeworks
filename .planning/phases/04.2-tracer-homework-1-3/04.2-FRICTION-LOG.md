# Phase 4.2 Friction Log — Tracer Homework 1.3

This log records where delivering the real homework `1_3-police-flasher` hurt, while the
work was fresh. It is the primary output of Phase 4.2: Phases 5 through 10 automate only
what this log proves painful (D-20). Each entry is a step of the delivery cycle, not a
bug report; the homework itself is the instrument that produced the evidence.

## How to read this log

Every entry carries the same seven fields:

- **step** — the delivery step in which the friction appeared;
- **what hurt** — the concrete obstacle, in the words of the person who hit it;
- **frequency** — how often a homework is expected to meet it;
- **cheap fix** — the smallest change that removes the hurt today;
- **automation candidate** — the script, hook, or generator that would pay off later;
- **what worked** — the existing repository mechanism that made the step possible;
- **minutes spent** — measured or estimated time lost to the friction.

`## Top automation candidates` stays empty until plan 07 synthesizes this log. The
`## Edge-probe dispositions` table is the no-silent-drop record for the fourteen
deterministic probe rows; its wording is fixed.

## Entries

### F-01 — Scaffold the homework from the template

| Field | Value |
|-------|-------|
| Step | Scaffold with `scripts/new_homework` |
| What hurt | The scaffold is idempotent but not obviously so: a second run reports `UNCHANGED` for all eight paths, so a verification that demands `CREATE` fails after the first successful run. The command also needs `UV_CACHE_DIR` pointed at a writable directory under `TMPDIR` in a sandboxed shell, or `uv` cannot create its cache. |
| Frequency | Every new homework; more than thirty are expected. |
| Cheap fix | Run the dry run first and accept `CREATE` or `UNCHANGED`; set `UV_CACHE_DIR` in the shell profile. |
| Automation candidate | A `new-homework` skill that wraps the dry run, the real run, the target build, and the native suite in one command (Phase 9). |
| What worked | `--dry-run --json` produced a machine-readable eight-record plan before any write, and a second real run was a clean `UNCHANGED` no-op. |
| Minutes spent | 0.14 min for the first target build (8.21 s), 0.81 s for the first native run; the whole scaffold step about 2 min. |
| Command | `UV_CACHE_DIR="$TMPDIR/uv-cache" uv run scripts/new_homework 1_3-police-flasher --template arduino` |
| Rendered paths | `platformio.ini`, `src/main.cpp`, `include/.gitkeep`, `test/test_homework/test_homework.c`, `assets/.gitkeep`, `README.md`, `task.md`, `homework.yaml` — all eight under `homeworks/1_3-police-flasher/`. |

### F-02 — Correct the provenance date and forward-declared paths

| Field | Value |
|-------|-------|
| Step | Provenance in `homework.yaml` and `task.md` |
| What hurt | Decision D-08 recorded `retrieved: 2026-10-23`. The checker's `valid_iso8601` requires a timezone, so the bare date is rejected; the failure only appears after the status flip to `in-progress`, because the scaffold's `planned` status still accepts the `TODO` sentinels. Separately, `homework.yaml` forward-declares `assets/diagram.json` and `report.md` before Waves 3 and 4 create them: the schema checks the path pattern, not whether the file exists on disk, so the metadata validates ahead of the artifacts. |
| Frequency | Once per homework for the timestamp shape, permanently; the forward declaration is one decision per homework. |
| Cheap fix | Write `2026-10-23T00:00:00Z`, and run `uv run scripts/check_metadata.py homeworks/<id>` before staging rather than trusting the hook to catch it. |
| Automation candidate | The Phase 5 generator should emit a timezone-bearing default instead of a bare date; the checker itself needs no change. |
| What worked | The checker failed loudly and named the exact field; after the correction it reported `OK` for both documents. The schema's `additionalProperties: false` confirmed the new `simulation`, `report`, and `assets` blocks were declared rather than invented. |
| Minutes spent | 5 min. |

### F-03 — Cold first build and test download their dependencies

| Field | Value |
|-------|-------|
| Step | First target build and first native test run |
| What hurt | The first native run installs the three symlinked libraries and downloads Unity 2.6.1 into `.pio/`; the first target build also attempts an outbound version check that a sandboxed shell denies. The green summary hides both, so a failed download looks like a build failure on the next run. |
| Frequency | Once per machine, and once per clean CI runner. |
| Cheap fix | Expect the cold downloads; ignore the version-check denial, which does not affect the artifact. |
| Automation candidate | CI caching of `~/.platformio/.cache` and `~/.platformio/packages` (Phase 8). |
| What worked | `pio run -d homeworks/1_3-police-flasher` finished with `SUCCESS` in 8.21 s, the native suite reported two cases with zero failures in 0.81 s, and no generated path became tracked or staged. |
| Minutes spent | 1 min waiting for the cold downloads. |
