## Phase Boundary

Run the real homework `1_3-police-flasher` through the complete delivery cycle manually and
record every friction point, so Phases 5–10 automate only what the log proves painful.

The phase delivers one real PlatformIO homework (Arduino, ESP32-S3 NTR8), its pure pattern
logic with native Unity tests, a Wokwi scenario, a concise but structurally complete report
with real evidence, the minimum manual integration edits, a minimal CI workflow for one
project, and one pull request. The friction log is the primary output; the homework is the
instrument that produces it.

This is a first pass, not the polished pilot. The `hw/1_3-police-flasher` tag is **not**
created here: Phase 11 ships the polished pilot. Generated views, the full CI matrix, the
simulation ADR, and the report contract remain with Phases 5, 7, 8, and 10.

A synthetic `0_0-gpio-tracer` homework was considered and explicitly rejected in favour of
the real assignment, because only the real homework exercises the actual artifact chain.

What must be true at the end: `homeworks/1_3-police-flasher/` is scaffolded through
`scripts/new_homework`, builds for the ESP32-S3 Arduino environment, runs its native Unity
tests, carries a real `assets/diagram.json` and `wokwi.toml`, has a report with BOM, pin map,
calculations, measurement ledger, and traceability, passes a single-project CI workflow, and
ships with `04.2-FRICTION-LOG.md` in this phase directory.

<decisions>
## Implementation Decisions

### Tracer scope and architecture

- **D-01:** The tracer is the **real** `1_3-police-flasher`, not a synthetic `0_0` exercise.
  A `0_0-gpio-tracer` was discussed and rejected: it would not exercise the real artifact
  chain, the real report, or the real simulation surface.
- **D-02:** This first pass implements the core plus **all four extensions**: third LED,
  variable speed, complex pattern, and single-GPIO operation. Implementations stay simple;
  Phase 11 owns polish.
- **D-03:** "Single-GPIO operation" means **two anti-parallel LEDs on one pin with a series
  resistor**: `HIGH` lights one LED, `LOW` lights the other. This matches the alternating
  police pattern and needs no extra active components.
- **D-04:** Framework is **Arduino** (`[env:esp32s3_arduino]`). The ESP-IDF template and
  adapter were already proven in Phase 4; duplicating the homework in ESP-IDF is out of
  scope for a tracer.
- **D-05:** The pattern logic lives **inside the homework**, not in `lib/common` (Phase 3
  D-12). The ceremony note's line "Pattern state machine in `lib/common`" is a planning
  sketch and is **superseded** for this phase. Promotion to `common` still requires real
  duplication across homeworks.
- **D-06:** The pure logic is a **homework-local private PlatformIO library** at
  `homeworks/1_3-police-flasher/lib/pattern/` with a `library.json`. Both the target and
  `[env:native]` compile it automatically, so the tests do not need `test_build_src = yes`
  or a fragile `build_src_filter`. D-12 is clarified as "within the homework", not
  literally under `src/`.
  — **Reversibility:** costly — moving the library later changes include paths, the native
  environment, and the tests; every future homework copies this shape.
- **D-07:** Native tests cover the pure logic **and** a controller that takes
  `port_gpio_t` / `port_time_t`, exercised with `host/fake_gpio` and `host/fake_time`. The
  full `setup()/loop()` is not unit-tested; its Arduino-specific composition is covered by
  the target build.
  — **Reversibility:** costly — the controller boundary is the test seam every later
  homework will mirror.

### Provenance and paraphrase

- **D-08:** `task.md` frontmatter:
  - `source_url: https://github.com/VLoktiev-EMB/homeworks`
  - `retrieved: 2026-10-23`
  - `attribution: Course handout 1.3 (paraphrased); original access-restricted and not redistributed`
  - `license: LicenseRef-Proprietary`

  `homework.yaml` `source.reference` carries the same URL, so the checker's cross-validation
  passes. The LMS URL is **not** published: it names the institution in its domain and its
  `/studying/<id>/` segment may carry a personal enrolment identifier.
  — **Reversibility:** costly — provenance is evidence captured at collection time and is
  not recoverable later; changing the shape touches every homework and the checker.
- **D-09:** The deferred META-02 UAT is closed by a **user checklist review before merge**:
  no verbatim sentences, no distinctive phrasing, no original file committed. The review is
  recorded in the pull request and in the report's decision appendix.
- **D-10:** Metadata status stays `in-progress` through this phase (no tag, Phase 11
  finalizes); `report.status` is `draft`; `simulation.status` is `pending` until Phase 7
  validates the tool.

### Evidence and report

- **D-11:** Evidence is a **hybrid**: the real board for build, flash, and serial, plus three
  real measurements — blink period (oscilloscope or logic analyzer), LED current
  (multimeter in series), and supply voltage (multimeter). Remaining values are
  `calculated`, `datasheet`, or `simulated`.
- **D-12:** Wokwi: author `assets/diagram.json` and `wokwi.toml` in the homework root and
  attempt a local run. `diagram.json` must declare `flashSize: "16"` and
  `psramType: "octal"`. If the custom 16 MB partition table requires a merged firmware
  image and blocks execution, record the friction and defer execution to Phase 7. No
  simulator-selection claim is made; ADR-0004 remains Phase 7.
- **D-13:** The measurement ledger uses all five labels — `measured`, `calculated`,
  `simulated`, `datasheet`, `not measured` — each with instrument, method, uncertainty, and
  the implementation commit hash. `Vf` is measured in the multimeter's diode mode and
  compared with the datasheet; the report explains the difference (diode-mode test current
  versus the operating current).
- **D-14:** Button debounce is **observed via serial timestamps** and labelled `observed`,
  not a precise measurement. An oscilloscope capture is optional only if the setup is
  already out for the blink period.
- **D-15:** The report is **structurally complete but concise**: all ten sections exist,
  with real content only where the assignment makes a section applicable. The BOM, pin map,
  electrical calculations, measurement ledger, and traceability matrix are real. The body is
  academic third-person English with IEEE references; a **decision appendix** records
  engineering decisions, dead ends, and friction.
- **D-16:** `README.md` is a short project index (purpose, status, links); `report.md` is the
  full report. Both live in `homeworks/1_3-police-flasher/`, matching the Definition of Done
  and the existing template README.

### Manual integration and CI

- **D-17:** Manual edits are limited to two: one entry in the root `README.md` and one folder
  in `homeworks.code-workspace`. `platformio.shared.ini` is **not** edited; the tracer
  records that a well-formed homework has no per-homework entries there. That finding is
  input for the Phase 5 generators.
- **D-18:** A **minimal single-project CI workflow** runs on pull requests: `pio run` for the
  ESP32-S3 Arduino environment and `pio test -e native` for the homework. No discovery
  matrix, no changed-only detection, no cache tuning. Phase 8 replaces it with the real
  matrix.
- **D-19:** One pull request on `hw/1_3-police-flasher` with atomic commits (scaffold, code
  and tests, assets, report, friction log, integration edits), squash-merged. **No `hw/`
  tag** in this phase.
- **D-20:** The friction log is written **live after each step**, then synthesized at the
  end. Each entry records step, what hurt, frequency, cheap fix, automation candidate, what
  worked, and minutes spent. The synthesis section `Top automation candidates` maps each
  candidate to Phases 5–10. The file is
  `.planning/phases/04.2-tracer-homework-1-3/04.2-FRICTION-LOG.md`.

### Claude's Discretion

- The internal split of `lib/pattern/` (state machine, timing helpers, controller) and the
  controller's exact API.
- The CI workflow's YAML details, cache keys, and timeouts.
- The friction-log table columns beyond the required fields, and the decision-appendix
  format in the report.
- The exact measurement procedure and the choice between oscilloscope and logic analyzer.

## Specific Ideas

- The user explicitly rejected a synthetic `0_0` tracer after considering it: the real
  homework is the only artifact that exercises the real chain. The decision is recorded so a
  later agent does not resurrect the synthetic idea.
- The user rejected publishing the LMS URL because it names the institution and may contain a
  personal enrolment identifier. The repository URL plus a neutral attribution is the
  preferred provenance.
- The user wants honest evidence labels over impressive-looking numbers; `not measured` is an
  acceptable and expected value.
- The Wokwi findings that shape D-12: the ESP32-S3 board defaults to 8 MB in Wokwi, the real
  target is 16 MB with octal PSRAM, and a custom partition table may require a merged
  firmware image. This is expected friction, not a reason to change the board configuration.
- The CI findings that shape D-18: changed-only detection needs a separate script, not the
  workflow `paths:` filter; a minimal single-project workflow is the honest tracer scope.
- The discussion happened in Ukrainian; this artifact is English per the project language
  constraint.
