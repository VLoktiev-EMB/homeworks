#### WR-03: `pattern_frame_at` переповнює `hold_ms` для великих `base_ms`

**File:** `homeworks/1_3-police-flasher/lib/pattern/src/pattern.c:118-119`

**Issue:** Добуток обчислюється в 32 бітах, але потім приводиться до `uint16_t` без перевірки. `pattern_frame_at(PATTERN_MODE_SOLID, 0u, 20000u).hold_ms` дає `14464`, тоді як очікується `80000`. Публічний API приймає будь-який `uint16_t base_ms`; таблиця швидкостей контролера (100/200/400) не досягає межі, але контракт її не декларує. Єдина таблиця з множником `hold_num > 1` — SOLID (`hold_num = 4`), тому межа для неї — 16 383; для решти рядків `hold_num = 1`, і добуток не переповнює `uint16_t` у всьому діапазоні `uint16_t base_ms`. Проблема виникає для будь-якого майбутнього джерела `base_ms > 16383` у SOLID. Коментар у `pattern.c` «no hold can round to zero» також спирається на припущення про таблицю швидкостей.

**Fix:** повертати `uint32_t hold_ms` (і відповідно змінити `pattern_frame_t` та виклики) або насичувати/обмежувати результат; якщо зміна типу небажана, задокументувати й перевіряти `base_ms <= 16383` для SOLID. Додати граничний тест `pattern_frame_at(SOLID, 0u, 20000u)`.

#### WR-04: Помилка `set_mode` для кнопки не повторюється і стирається першим tick

**File:** `homeworks/1_3-police-flasher/lib/pattern/src/controller.c:173-174`, `:251`, `:134-137`, `:180-182`

**Issue:** `pattern_controller_init` конфігурує `pin_a`/`pin_b`/`pin_c` і `button_pin`. Вихідні піни повторюються через `apply_pin` (стан `applied` скидається), але `set_mode(..., PORT_GPIO_INPUT_PULLUP)` для кнопки викликається лише в init. Якщо цей виклик повертає помилку, init її повертає і все одно встановлює `ready = true`; перший `pattern_controller_tick` перезаписує `controller->status` значенням `PORT_OK` і більше ніколи не налаштовує кнопку. Доведено власним `port_gpio_t`, у якому `set_mode(7)` повертає `PORT_ERR_IO`: `init status = 2`, після одного tick `status = 0`, кількість викликів `set_mode` для піна 7 = 1. На Arduino-адаптері `pinMode` не може повернути помилку, тому цільова збірка не зачеплена; але контракт порту й fake можуть повернути помилку, а коментар у коді обіцяє, що runtime-помилки повторюються. Кнопка може залишитися плаваючою і давати хибні натискання.

**Fix:** додати `bool button_configured` у `pattern_controller_t`; встановлювати його лише після успішного `set_mode`; у `pattern_controller_tick` повторювати `set_mode(INPUT_PULLUP)`, поки він не вдасться, і зберігати цю помилку в статусі до успіху. Додати тест із вибірковою відмовою для піна кнопки (розширити fake або використати власний порт).

**Класифікація:** WARNING.

#### WR-06: Неправильний фізичний аналіз низького стану півмоста: LED1 бачить прямий, а не зворотний зсув

**File:** `homeworks/1_3-police-flasher/report.md:107-109`, `:176` (C-04)

**Issue:** У низькому стані струм тече `3V3.1` → LED2 → вузол X → R1 → GPIO4; X ≈ 3.3 V − Vf2 ≈ 1.4 V. Зворотний зсув має лише LED2 у високому стані (рядок C-04). **Fix:** переписати речення: «LED1 бачить ≈1.4 V прямого зсуву, нижче порогу провідності, тому залишається вимкненим»; уточнити, що C-04 стосується LED2 у високому стані; за потреби додати в розрахунки/L-12 прямий off-state зсув LED1.

#### IN-08: Safety-правило «never parallel two LEDs onto one resistor» суперечить спільному R1

**File:** `homeworks/1_3-police-flasher/report.md:186-189`

**Issue:** Півміст навмисно використовує один R1 для LED1 і LED2 (anti-parallel, провідний лише один у кожному стані). Правило про «parallel two LEDs onto one resistor» стосується паралельних однойменно-орієнтованих LED із current hogging, але в контексті цієї схеми читається як заборона власного дизайну.

#### IN-09: Debounce не захищений від зворотного стрибка годинника
