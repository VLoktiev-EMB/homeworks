<objective>
Close G-09-1: a confirmed upload followed by
`uv run scripts/serial_capture.py --id 1_3-police-flasher --seconds 20` must capture real device
bytes instead of reporting `capture unavailable: no bytes captured`.

Measured root cause (`.planning/debug/capture-no-bytes.md`): `_build_command` omits `--dtr` and
`--rts`, so `pio device monitor` opens the port with pyserial's defaults, both lines asserted. On
the ESP32-S3 an asserted RTS pair is the chip-reset state through the USB-Serial-JTAG peripheral
on the native USB port (`USB VID:PID=303A:1001`) and through the auto-reset circuit on the CH343
UART bridge (`USB VID:PID=1A86:55D3`). The application never runs, so the capture collects
nothing. Measured outside the sandbox: default monitor 0 bytes; `--dtr 0 --rts 0` returned 248
bytes on the CH343 port and 282 bytes on the native USB port, both ending in `I pattern ready`.
A sandboxed run is not a valid measurement because opening `/dev/cu.*` is refused.

The same measurement exposed a second ambiguity: with both cables attached, two plausible USB
serial devices exist (`303A:1001` and `1A86:55D3`) and PlatformIO's implicit selection picks one
without telling anyone. This plan therefore makes port selection explicit and fail-closed, and
records the resolved identity so a log can always be traced to the interface that produced it.

Purpose: make the helper open the port in the idle line state, target exactly one deterministic
device, and report which device and baud it used.
Output: port and baud resolution, the new argv, identity reporting in both output modes, and the
regression suite that pins all of it.

Design choice: always pass `-p <resolved>` rather than letting the monitor choose, and refuse
when the candidate set is not exactly one. The log stays byte-exact raw device output; the port
metadata lives only in the JSON object and the stdout line.
</objective>
