## Summary

The deletion side of this phase is clean. Removing the Cyrillic allowlist from
`scripts/metadata/contract.py` left no dangling symbol, no stale keyword argument and no
orphaned reference: `load_allowlist`, `apply_allowlist`, `CYRILLIC_RULE`, `ALLOWLIST_PATH`
and every `rule=` call site are gone, `check_metadata.py` no longer imports them,
`temp_root.py` no longer copies the deleted file, and `scripts/new_homework` reads only
`path`/`status`/`reason` from `validate_candidate`, so the narrower record shape breaks
nothing. The checker passes on the live tree, `scripts/check_architecture.py` still exits 0
with all four PASS lines, both YAML files parse, and the surviving suite is 81/81 green
(`python3 -m unittest discover -s scripts/tests`). The allowlist removal is a net security
improvement: a Cyrillic exemption now requires a visible code edit instead of a data-file
entry.

The failures are concentrated in the two artefacts the phase rewrote rather than deleted:
`scripts/tag_homework.sh`, whose fail-closed semantics did not survive the rewrite, and the
enforcement claims that `AGENTS.md` and `.pre-commit-config.yaml` still make about hooks that
cannot see the paths the repository actually uses.

The two Critical findings were reproduced against a throwaway repository with a local bare
`origin`; they are not theoretical. Both create a **permanent, unmovable public tag pointing
at a commit that does not contain the homework** — the exact failure the deleted precondition
list existed to prevent, and the deleted `scripts/tests/test_tag_homework.py` contained the
case (`test_homework_absent_from_the_tag_target_is_refused`) that would have caught it.

## Critical Issues

### CR-01: Tag script publishes at a stale `origin/HEAD` — the remote-tracking ref is never refreshed

**File:** `scripts/tag_homework.sh:33-34`
**Issue:** The script resolves the tag target from the local remote-tracking ref and never
fetches:

```bash
base="$(git rev-parse "$(git symbolic-ref --short refs/remotes/origin/HEAD)")"
git tag "hw/$id" "$base"
```

`refs/remotes/origin/main` only moves on `fetch`/`pull`. The normal maintainer flow — squash
merge in the GitHub UI, then run `scripts/tag_homework.sh <id>` locally — leaves that ref on
the pre-merge commit. The tag is then created and pushed at the pre-merge commit with exit 0,
and a published tag cannot be moved.

Reproduced end to end (local bare origin, merge pushed from a second clone, tag run from a
clone that had not fetched):

```text
origin/main as maintainer sees it: 7cc4364...
actual merged commit on origin:     ac1c941...
To .../origin.git
 * [new tag]         hw/1_3-demo -> hw/1_3-demo
script exit=0
tag points at: 7cc4364...
does the tagged commit contain homeworks/1_3-demo?  NO
remote tag after push: hw/1_3-demo
```

The removed script did `git fetch --quiet origin` and then asserted
`git cat-file -e "$base:homeworks/$id"` before creating anything; both gates are gone. The
header comment still promises "The tag is created at the origin default branch", which is
only true as of the last fetch.

Secondary defect in the same expression: `--short` strips `refs/remotes/`, so `rev-parse`
gets the ambiguous shorthand `origin/main`. Git resolves `refs/tags/origin/main` before
`refs/remotes/origin/main`, so a local tag of that name silently redirects the target. The
removed script's explicit `refs/remotes/origin/$DEFAULT_BRANCH` had no such ambiguity.

**Fix:**
```bash
# Refresh first: a stale base publishes a permanent tag at the wrong commit.
git fetch --quiet origin || { echo "FAIL base: cannot fetch origin" >&2; exit 1; }

default_ref="$(git symbolic-ref --quiet refs/remotes/origin/HEAD)" ||
  { echo "FAIL base: refs/remotes/origin/HEAD is not set" >&2; exit 1; }
default_branch="${default_ref#refs/remotes/origin/}"

if ! base="$(git rev-parse -q --verify "refs/remotes/origin/$default_branch")"; then
  echo "FAIL base: cannot resolve origin/$default_branch" >&2
  exit 1
fi
```

### CR-02: Nothing verifies that `homeworks/<id>` exists at the tag target, so any well-formed ID produces a permanent tag on `main`

**File:** `scripts/tag_homework.sh:34-35`
**Issue:** The rewrite dropped the only content check. A valid-shaped ID that names no
homework — a typo, a not-yet-merged homework, or a wrong module number — is tagged and
pushed with exit 0:

```text
no homeworks/ dir exists:
To .../origin.git
 * [new tag]         hw/9_9-ghost -> hw/9_9-ghost
exit=0
hw/9_9-ghost
```

`AGENTS.md:121-123` still makes this script "the only tag path" and still says the tag is
created "after the homework pull request is merged". The check that made the second half of
that sentence true — `git cat-file -e "$base:homeworks/$id"`, which tests the *committed*
tree rather than the working tree — was removed, so the rule is now review-only while the
rulebook presents the script as the guard. Because tag refs carry no ruleset and a published
tag is never moved (`AGENTS.md:83-84`), the damage is permanent.

This is also the mechanism that would have masked CR-01: with the check restored, a stale
base would fail closed instead of publishing.

**Fix:** Add the content gate before creating the tag, using the `base` resolved in CR-01:
```bash
if ! git cat-file -e "$base:homeworks/$id" 2>/dev/null; then
  echo "FAIL homework: homeworks/$id is absent from $default_branch ($base)" >&2
  exit 1
fi
```

## Warnings

### WR-01: Tag script's exit codes and diagnostics no longer match its own contract

**File:** `scripts/tag_homework.sh:15-17,33-35`
**Issue:** The header documents `1 the default branch could not be resolved, or
creation/push failed`, but `set -e` leaks git's own status. Observed: a repository without
`origin/HEAD` exits **128** with raw `fatal:` lines, and re-running after an existing tag
exits **128** with `fatal: tag 'hw/1_3-y' already exists`. There is no `FAIL`-prefixed line
and no recovery hint. The removed script printed one `FAIL <gate>:` line per precondition,
exited 1, and told the operator that a failed push leaves a local tag removable with
`git tag -d`. That hint is now essential and absent: if the push fails, the local tag
survives and every retry dies at `git tag` with 128, so the operator must guess.

**Fix:** wrap the two git calls and normalise the status, e.g. `git tag "hw/$id" "$base" ||
{ echo "FAIL create: git tag hw/$id failed" >&2; exit 1; }` and the same for the push with
"the local tag remains; remove it with 'git tag -d hw/<id>'", and update the header's exit
code list to what the script actually returns.

### WR-02: `no-generated-files` cannot see any generated path under `homeworks/` — its literal pathspecs only match the repository root

**File:** `.pre-commit-config.yaml:41-46`
**Issue:** `git ls-files -ci --exclude-standard -- compile_commands.json site .pio …` matches
those names at the root only. Every PlatformIO project — and therefore every `.pio/`,
`compile_commands.json` and `site/` build — lives under `homeworks/<id>/` (`tests/.pio/` and
`tests/compile_commands.json` already exist in the working tree). Reproduced with the hook's
real entry string against a fixture where four ignored generated paths were `git add -f`'d:

```text
exit: 1
stderr: tracked generated paths:
compile_commands.json          # the only one reported
```

`homeworks/1_3-x/compile_commands.json`, `homeworks/1_3-x/.pio/build.json` and
`homeworks/1_3-x/site/index.html` were all tracked and all invisible. `AGENTS.md:146-149`
states this hook as the `[ENFORCED: pre-commit]` proof that "Generated files are never
committed" and explicitly notes that `.gitignore` alone cannot stop `git add -f`; for the
repository's mandatory layout it currently enforces nothing.

**Fix:** use recursive pathspecs, or drop the pathspec and filter in the shell:
```yaml
entry: >-
  bash -c 'tracked=$(git ls-files -ci --exclude-standard --
  compile_commands.json "**/compile_commands.json" site "**/site" .pio "**/.pio"
  "homeworks/*/CMakeLists.txt" "homeworks/*/src/CMakeLists.txt" "homeworks/*/sdkconfig.*")
  || exit 1; …'
```

### WR-03: The metadata hook does not run when its own source of truth changes

**File:** `.pre-commit-config.yaml:76`
**Issue:** `check_metadata.py` reads `platformio.shared.ini` and fails every homework whose
`toolchain.platform` disagrees with the pin (`contract.py:read_shared_platform_pin`,
`contract.py:558-566`). The schema only constrains the shape
(`^[a-z0-9-]+@[0-9]+\.[0-9]+\.[0-9]+$`), so the shared file is the sole truth for the pin. It
is absent from the hook's `files` pattern, so bumping the platform in
`platformio.shared.ini` runs no hook at all and leaves every existing `homework.yaml`
silently drifted until some other file under `homeworks/` happens to change. After the
retirement of `test_metadata_deps.py`, this was the other pin-drift gate and it is the only
one left.

**Fix:** add the file to the pattern, e.g.
`^(homeworks/|schema/|platformio\.shared\.ini|scripts/check_metadata\.py|scripts/new_homework$|scripts/metadata/)`.

### WR-04: The only guard on an irreversible published artefact now has zero automated coverage

**File:** `scripts/tag_homework.sh` (test module deleted in `17b1a2f`/plan 04.1-06)
**Issue:** `scripts/tests/test_tag_homework.py` was deleted with the meta-test sweep, and it
was not a meta-test: it ran the real script against a disposable git repository with a local
bare `origin` and asserted the refusal paths. Its docstring named the exact regression this
review found ("a homework present only in the working tree, not at the tag target commit, is
refused — the tag must never point at a commit without the homework"), and its
`test_existing_tag_is_refused` was the only executable proof that a published tag is never
moved. Nothing replaced it, no hook lints shell scripts, and `AGENTS.md` still routes tagging
through this script alone.

**Fix:** restore a minimal offline suite (the fixture harness in the deleted module is
reusable) covering: missing `homeworks/<id>` at the base commit, an existing local tag, and a
stale base — or, if the suite stays deleted, record the tag script as `[ENFORCED: review]`
rather than presenting it as a guarded path.

### WR-05: `AGENTS.md` keeps `[ENFORCED: CI]` on rules that no repository check backs, and deletes the paragraph that defined the markers

**File:** `AGENTS.md:53-54,80-84`
**Issue:** The rewrite shortened the marker legend to a bare list, dropping the definitions
("`[ENFORCED: CI]` in repository automation or a CI drift check"). Every rule still uses the
vocabulary. Two rules keep `[ENFORCED: CI]` although the phase deleted the only check that
proved them (`scripts/check_policy.py`, `policy/`) and the workflow now contains a single
gitleaks job: "Never push directly to the default branch" and "Published history is never
rewritten". The prose correctly says the ruleset "is maintained in the GitHub UI", but the
marker contradicts it — the setting is enforced server-side by an out-of-band UI value that
nothing in the repository verifies (`04.1-SECURITY.md` AR-4.1-01 records exactly that gap as
an accepted risk). The licence rule was correctly downgraded from CI to review; these two
were not.

**Fix:** restore one sentence defining the three markers, and change those two rules to
`[ENFORCED: review]` (or introduce an explicit `[ENFORCED: server-side]` marker) so no rule
claims a check that does not exist.

### WR-06: The quick-start no longer runs the surviving test suite

**File:** `AGENTS.md:17-24,33`
**Issue:** The four-row quick-start runs the build, the native suite, pre-commit and the
metadata checker. The rules section still requires a GSD tier (`AGENTS.md:58-62`), and the
layout still advertises "`scripts/tests/` — the test suite", but no documented step runs it

regression proof for INV-01 and the metadata contract, and nothing catches them going red.
The phase's own summary lists "the discovered suite passes" as a gate, so the omission is

**Fix:** add the row back, e.g.

### IN-01: PR template commands omit the `-d` target that `AGENTS.md` requires

**File:** `.github/pull_request_template.md:11-13`
**Issue:** The single template is now the only contributor-facing checklist, and it says
`pio run` and `pio test -e native`. `AGENTS.md:21-22` specifies `pio run -d <project>` and
`pio test -d tests -e native`, and the repository root has no `platformio.ini`, so the
template's commands cannot be pasted at the root the template is read from. `pio test -e
native` is valid *inside* a homework project (each declares `[env:native]`), so the two
readings are both defensible — the template should say which. It also omits item 5 of the
Definition of Done (the `hw/<id>` tag).
**Fix:** spell the target out, e.g. "`pio run -d homeworks/<id>` is green" and
"`pio test -d tests -e native` (shared libraries) or `pio test -e native` inside the
homework is green".
