**Copy the house workflow style from `.github/workflows/homework.yml`.** Same `runs-on:
ubuntu-24.04`, same SHA-pinned `uses:` with the release tag in a trailing comment and the existing
comment explaining why a commit SHA is used instead of a mutable tag, same
`persist-credentials: false` on checkout, same `concurrency:` shape.

**Two workflow files, not one (RESEARCH Open Question 5).** `generated-views.yml` is a pull-request
gate with `contents: read`; `docs.yml` is a `main`-only deploy with `pages: write` and
`id-token: write`. A single file would need the deploy job skipped on every pull request, and
Phase 8's `meta` job will want a third file anyway.

**Checkout without LFS.** Pages cannot serve LFS objects, and a default checkout leaves a 130-byte
pointer where an image should be. Check out with `lfs: false` stated explicitly, and call the
separately testable `scripts/ci/check_lfs_pointers.sh site` in its own step (see the guard-script
paragraph below).

**No `gh-deploy`.** `mkdocs gh-deploy` pushes a `gh-pages` branch, which bypasses the branch and
pull-request rules in `AGENTS.md`. Use `upload-pages-artifact` plus `deploy-pages` with OIDC and the
`github-pages` environment.

**Revalidate the action pins before writing.** The research-resolved commits are
`configure-pages@v6` → `45bfe0192ca1faeb007ade9deae92b16b8254a0d`,
`upload-pages-artifact@v5` → `fc324d3547104276b827a68afc52ff2a11cc49c9`, and `deploy-pages@v5` →
`368f82528645a54fb793d4d04e342629a3f51346`. `actions/checkout@v7.0.1` →
`3d3c42e5aac5ba805825da76410c181273ba90b1` and `actions/setup-python@v7.1.0` →
`6d4fd22b20465ccc0f7354476588e8df7c9ca0e0` are already in use in `homework.yml`. Run
`git ls-remote https://github.com/<owner>/<repo> refs/tags/<tag>` for each immediately before
writing and use the revalidated value if it differs.

**Install the docs stack with pip in CI, `uv` locally.** CI already pins `actions/setup-python`, so
`python -m pip install -r requirements-docs.txt` avoids adding a fourth action.

**The pre-commit hook must not depend on `uv`.** The `check-metadata` hook already builds an
isolated environment from `additional_dependencies`; `gen-views-check` follows the same shape with
`language: python` and only `PyYAML==6.0.3`. That pin set is now correct, not optimistic: 05-01
moved the pure helpers to `scripts/metadata/paths.py` and the strict loader to
`scripts/metadata/yaml_loader.py`, and 05-03's `ModuleBoundaryTests` asserts that importing
`scripts.gen_views` never loads `jsonschema` or `scripts.metadata.contract`. If this hook fails
with `ModuleNotFoundError`, the import boundary regressed; fix the boundary rather than adding
jsonschema to the hook.

**Probe every drift class, not only the easiest one.** A one-byte edit to `mkdocs.yml` proves the
happy path of the gate. Also perturb a generated page (`docs/homeworks/<id>.md`), `generated.manifest`
alone, and add an orphaned `docs/homeworks/9_9-ghost.md`. Restore the tree after each probe and
finish with a clean hook run. The manifest-only probe is the one that catches a check that compares
files but forgets the ledger.

**The LFS guard is a script, so it can be tested (review finding).** Grepping the workflow YAML
proves only that the text exists. Put the guard in `scripts/ci/check_lfs_pointers.sh`: it takes a
directory argument, scans regular files for `git-lfs.github.com/spec/v1`, prints each offending
path on stderr, and exits 1 on the first hit (0 when clean). The workflow calls
`bash scripts/ci/check_lfs_pointers.sh site` in its own step, and
`scripts/tests/test_ci_workflows.py` runs the script against a temporary directory with and without
a pointer. That is a real test of the behaviour rather than of the YAML string.

**`AGENTS.md` has two `docs/standards/` lines, not one.** Line 39 (the "Planned:" sentence) and line
192 (the routing-table row). Fixing only one leaves the routing table lying (D-12). The new layout
paragraph must not introduce a third mention: describe the generated tree without naming
`docs/standards/`. The test asserts exactly two lines and both say Phase 10.

**Pages setup is a maintainer action, not a workflow step (review finding).** `deploy-pages`
requires `Settings -> Pages -> Build and deployment -> Source = GitHub Actions`, and a
`workflow_dispatch` on a feature branch cannot prove the deploy path because the environment and
the Pages source are repository settings. Record the checklist item in this plan and in the PR
body; verify the first real deployment after the merge to `main`, and treat the `docs` workflow's
`build` job (strict build plus LFS guard) as the pre-merge evidence.
