<objective>
Close CR-01 and CR-02 of gap G-10-1: the report checker must turn a hostile `homework.yaml` or `assets/diagram.json` into a content record at exit 1 with a valid `--json` array, never a `RecursionError` traceback.

A pull request can commit a roughly 2 KB `homework.yaml` with 1,000 nested flow sequences, or a 200 KB `assets/diagram.json` of 100,000 nested arrays. Both are valid syntax and both sit inside the declared size gates. Today PyYAML's recursive parser and `json.loads` exhaust the Python stack; `_read_metadata` catches only `yaml.YAMLError` and `parse_diagram` catches only `json.JSONDecodeError`, so the exception escapes, `main` prints a traceback, exits 1 with empty stdout, and the `--json` array never appears. That contradicts the module's documented exit-code contract (D-04: a content problem stays at exit 1 with a record) and `parse_diagram`'s docstring "never raises" (T-10-27).

Purpose: the gate reports a hostile document instead of crashing, and `check_metadata.py`, which shares `StrictSafeLoader`, inherits the same YAML bound.
Output: a bounded `StrictSafeLoader`, recursion-safe `_read_metadata` and `parse_diagram`, and regression tests at the checker and loader levels.
</objective>

The depth bound is set to 64. The deepest shipped metadata block is about four levels, so 64 is generous; a real document that needs more is a contract change, not a reason to raise the bound quietly.

The report checker's `_read_metadata` keeps a `RecursionError` clause even though the loader guard now raises `yaml.YAMLError` first. That clause is deliberate defence in depth: the contract is "never a traceback", and a future loader replacement must not be able to reintroduce one.
